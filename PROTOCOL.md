# The PixelBench protocol

Everything below is implemented in this release; the file that implements each part is named in its section.

## Tasks (`tasks/`)

- **Text-to-image (75 tasks).** A task statement, a native canvas from 16x16 to 256x256, and a ceiling on the number
  of visible colors. The model starts from an empty transparent canvas. The tasks cover seven subjects: characters,
  creatures, scenes and architecture, objects, icons and interface, materials (seamless tiles), and effects.
- **Editing (25 tasks).** An input artwork and an instruction: 13 instruction edits, 10 animations (2 or 3 frames),
  and 2 multiview turnarounds. The model chooses the output canvas; all frames of a result share one size. There is
  no color ceiling.
- **References.** Each task has one reference image, used by the judge's final protocol and shown to the raters
  who ranked with references; the model never sees it. For text-to-image it is a GPT-Image-2 rendering of the task
  statement; for editing it is either the source's own target frames (13 tasks) or a GPT-Image-2 edit of the same
  instruction (12 tasks). `tasks/*/*/reference.png` is the reference exactly as the judge receives it.

## Creation (`pixelbench/protocol.py`, `scripts/run_benchmark.py`)

- **Environment.** The model works in a file workspace through five tools: `write_file`, `edit_file`, `read_file`,
  `list_files`, and `run(path, submit)`. Every run executes the current program from the task input in a fresh
  process. A program declares its output with `finish(canvas)` or `finish([f1, f2, ...])`; `run(..., submit=True)`
  ends the episode when the whole program succeeds. With image observation, `view(canvas)` returns the rendered
  canvas as an image; without it, the model reads the canvas as text (`matrix_text`, `stats_text`). The system
  prompt and the drawing API reference are generated by `pixelbench/repl/file_docs.py`; the prompt carries no
  pixel-art technique guidance and no example artwork.
- **Budgets.** At most 25 writes of program source on a text-to-image task and 15 on an editing task
  (`write_file` and `edit_file` calls); reading and running do not count. A program run is limited to 120 seconds.
- **Time limits.** A single model request is cut after 75 minutes and a task after three hours; a cut episode keeps
  its intermediate result.
- **Submission.** When a run ends without a formal submission, the environment recovers the artwork from the canvases
  the program drew.
- **Sandbox** (`pixelbench/repl/sandbox.py`). Before the first line of a model's program runs, its process is confined
  with Landlock and seccomp: it can read and write only its own run directory, read the Python installation and the
  `pixelbench` package, and it cannot open network sockets or start other programs. The sandbox is always on;
  `--unsafe-no-sandbox` turns it off for platforms without Landlock, and such results are not comparable.
- **Reruns.** A failure of the serving infrastructure (a 5xx or 429 response, an exhausted quota, a dropped
  connection) says nothing about the model: the task is run again from the start until it completes. When the model
  itself returned no artwork, was cut off by a time limit, or submitted only fully transparent frames, the task is
  rerun once with the same configuration, and the rerun counts. `run_benchmark.py` applies this rule and records
  every attempt.

## Configurations (`configs/models/`)

The twelve configurations of the main table, the reasoning-effort variants, and GPT-6 Astra without image
observation. A configuration lists the request fields sent to the model (`llm`) and whether it observes images
(`vision`); `reported_level` is the reasoning setting the paper reports. Creation runs 2 and 3 of the
repeated-creation analysis repeat the base configuration. The direct-answer baseline (`scripts/run_direct.py`) uses
the base configuration: one answer with a palette and one code per pixel, at most 131,072 tokens and 60 minutes, no
tools and no second turn.

## Judge (`pixelbench/eval/judge_protocol.py`, `scripts/run_judge.py`, `configs/judge.json`)

- **Protocol versions.** Four cumulative versions: `e0_base` (minimal prompt), `e1_margin` (+ a transparent margin of
  1/16 on the left and top of every pixel-art image), `e2_rubric` (+ a rubric for the task family and subject), and
  `e3_reference` (+ the task's reference image). The final protocol is `e3_reference`.
- **Images.** Frames are packed into the most nearly square grid, a material tile is repeated 2x2, the margin is
  added, and the image is scaled with nearest-neighbor sampling so that its longer side is 512 pixels. An editing
  task always shows the original artwork first; when the task asks the first frame to reproduce the original, only
  the generated frames are shown.
- **Settings.** GPT-6 Astra at reasoning effort xhigh and temperature 0.2; one user message per artwork; at most four
  attempts; only a bare number from 0 to 100 counts as a score. One pass per artwork.
- **Development subset.** The prompt wording was settled on 23 generation tasks before any artwork of the evaluation
  was created (`development_subset` in `tasks/index.json`).

## Human ranking (`data/human/`)

Ten raters with professional art backgrounds each ranked the twelve artworks of every one of the 100 tasks in an
offline page. Cards carry random labels, start in a random order drawn per rater and task, are magnified with
nearest-neighbor sampling, and animations play in a loop. The rater drags the cards into a Z-shaped order (ranks 1-6
in the top row, 7-12 in the bottom row). Eight raters saw the task's reference image; two ranked without any
reference (for editing they saw only the original).
